## 1. Executive summary — the five that matter most

1. **The moderation queue is optional.** Any self-registered agency account can move its own
   draft straight to `published` (`app/agencia/actions.ts:19`), bypassing the review queue
   the entire trust story rests on. (F1)
2. **Stored XSS is reachable.** JSON-LD is inlined without escaping `<` (`src/components/JsonLd.tsx:3`),
   so an attacker-controlled listing description can execute script on the public origin —
   and F1 gives them the publish path, with no CSP to blunt it. (F2)
3. **The CSV importer silently divides prices by ~1000.** `85.000` (es-PY thousands) parses as
   `85` (`src/lib/import/csv.ts:75`), writing a $85 listing that then poisons the medians,
   /precios and /tasacion. (F3)
4. **A listing published through the site's own wizard has no contact method and its leads
   vanish.** The wizard never sets `agent_id`/contact, so the WhatsApp button doesn't render,
   the lead routes `internal` and never reaches the publisher's inbox, and the agent's profile
   shows "no listings". The core conversion loop is broken. (F4)
5. **Every public page is dynamic-per-request with no route cache.** A crawler walking the
   sitemap is N full React renders on a 200-process shared host — the same pressure that
   caused the documented 503 spiral. (F17)

## 3. Detail by severity

### P0

**F1 — Moderation queue is bypassable.**
`app/agencia/actions.ts:17` lists `AGENCY_STATUSES` including `"published"`, and both
`setListingStatusAction` and `agencyUpdateListingAction` → `updateListing`
(`src/lib/listing-edit.ts:265`) accept it with no check of the row's current status. So the
publish wizard's `pending_review` gate and the whole review queue are advisory: a
self-registered account (registration is open, `src/lib/registration.ts`) moves its own draft
— or a previously **rejected** listing — straight to `published`. This contradicts the
promise made at `/registro` ("revisamos cada aviso") and in `registration.ts:7`.
*Who notices:* every visitor (unmoderated spam/scam content); it is also the delivery path for F2.
*Fix:* drop `published` from `AGENCY_STATUSES`; the only path to `published` should be an
admin `approveListing`. Let agencies set draft/paused/sold/rented and re-submit to
`pending_review`.

**F2 — Stored XSS via unescaped JSON-LD.**
`src/components/JsonLd.tsx:3` does `JSON.stringify(...)` into `dangerouslySetInnerHTML`.
`JSON.stringify` does not escape `<` or `/`, so a DB string containing `</script><script>…`
closes the tag and executes. Attacker-controlled sources reaching a JSON-LD emitter:
`listing.title`, `listing.descriptionEs` (`src/lib/jsonld.ts:35`), listing titles in
`itemListJsonLd`, agency/agent names in `breadcrumbJsonLd`. Description is never
content-limited (`app/publicar/actions.ts:99`). Combined with F1 (open publish path) and F20
(no CSP), this is fully exploitable by any internet user.
*Fix:* escape before inlining — replace `<`, `>`, `&` with their `\uXXXX` forms in `JsonLd`
(single choke point, fixes every call site at once). Add a CSP (F20) as defence in depth.

**F3 — CSV importer silently mangles thousands-dotted numbers.**
`src/lib/import/csv.ts:75` `num()` does `Number(s.replace(/[^0-9.-]/g, ""))`, treating `.` as
a decimal point. An es-PY spreadsheet cell `85.000` (= 85 000) becomes **85**; `1.250.000`
becomes `NaN` and the row is rejected loudly — so the dangerous case is the quiet one: a
single-group thousands value writes `price_usd = 85.00`, which poisons `market_medians`,
`/precios`, and `/tasacion`. `area_m2` `1.200` → 1.2 m² corrupts the area bucket too. The link
importer already has a correct locale-aware `parseAmount()` (`src/lib/import/from-url.ts:149`)
— two ingest paths, two different money parsers.
*Fix:* move `parseAmount()` into `normalize.ts` and have `csv.ts` use it; add a sanity floor
on `price_usd` (reject/flag anything below, say, 1000 for USD sale prices).

### P1

**F4 — Publisher-identity gap: self-published listings have no contact and lost leads.**
The wizard writes the OTP/verified WhatsApp to `users.whatsapp`
(`app/publicar/actions.ts:188`) and stamps only `ownerUserId` on the draft
(`src/lib/publish-queries.ts:186`); it never sets `agentId`, and `listings` has no contact
column. So on the detail page `contactWhatsapp = agent?.whatsapp ?? agency?.whatsapp ?? null`
(`app/propiedad/[slug]/page.tsx:131`) resolves to `null` for an independent/FSBO publisher —
the sticky card, panel form and mobile CTA bar all render with **no WhatsApp link**. The lead
then routes `internal` (`app/api/leads/route.ts:56`), which `getPanelLeads` filters out
(`src/lib/panel-queries.ts:534`), so the publisher's inbox stays empty while the buyer is told
"Tu consulta llega directamente al vendedor". And `/agente/[slug]` joins on `agents.id`, so the
listing never appears on its publisher's own profile.
*Fix:* add `ownerUser.whatsapp` to the `contactWhatsapp` fallback chain; and/or copy the
verified number onto the `agents` row at publish so lead routing, contact, and profile all
resolve. This is one missing link between the wizard and the `agents` table — decide whether an
independent publisher gets an `agents` row or the listing carries a contact column.

**F5 — `wa.me` links have no country code.**
All 9 WhatsApp link builders do `.replace(/\D/g, "")` on a raw phone
(`app/propiedad/[slug]/page.tsx:591`, `src/components/ContactForm.tsx:73,162`,
`SiteFooter.tsx:51`, `app/contacto/page.tsx:34`, `app/inmobiliaria/[slug]/page.tsx:131`,
`app/desarrolladora/[slug]/page.tsx:111`, `app/agencia/leads/page.tsx:29`,
`app/admin/leads/page.tsx:50`, `app/page.tsx:90`). A number typed as `0981 234 567` yields
`https://wa.me/0981234567` → WhatsApp error page.
*Fix:* one `waLink(phone, text)` helper that normalises to E.164 with a configured default
country prefix (`+595`), used in all 9 places; normalise on write in `registration.ts` and the
profile forms. (Also the template abstraction — see §5.)

**F6 — No `metadataBase`.** `app/layout.tsx` sets none, and the homepage OG image is the
relative `/img/og-share.webp` (`app/page.tsx:83`). Next 15 with no `metadataBase` and no
`VERCEL_*` falls back to `http://localhost:3000`, so the `og:image` is unfetchable — a bare
grey link when shared on WhatsApp, the primary sharing channel.
*Fix:* `metadataBase: new URL(await siteOrigin())` in the layout `generateMetadata`.

**F7 — Most page types emit no OG tags.** Next only emits OG if `metadata.openGraph` is
truthy, and the root layout sets none — so the entire category tree, /precios, profile pages,
proyecto, tasacion, and legal pages produce zero OG output. Any category or profile link
pasted into WhatsApp is a bare link.
*Fix:* set a default `openGraph` (siteName from `await brandName()`, the og-share fallback) in
the layout; per-page objects merge over it.

**F8 — Sitemap vs page indexability divergence.** `src/lib/sitemap.ts:162` gates a barrio page
on `cityIndexable` (city, all types), but the page
(`app/[operacion]/[...segments]/page.tsx:176`) gates on city **+ type** count ≥ 3. A busy city
with a rare type submits a URL in the sitemap that renders `noindex` — the exact "submitted URL
not selected as canonical" condition.
*Fix:* key the sitemap's barrio parent gate on the city+type count, matching the page.

**F9 — ItemList JSON-LD on the wrong origin.** `app/inmobiliaria/[slug]/page.tsx:80` and
`app/agente/[slug]/page.tsx:87` pass `siteOrigin()` to `itemListJsonLd`, but the items are
listing-detail URLs whose canonical host may differ. On inmobiliaria.com.py this publishes
`https://inmobiliaria.com.py/propiedad/…` in structured data while the page's own
`<link rel=canonical>` points at realestateinparaguay.com. (The category page got this right at
`page.tsx:252` — copy that.)
*Fix:* resolve `listingCanonicalOrigin()` separately and pass it for the item URLs.

**F10 — Dead contact email in 8 user-facing places.** `hola@propia.com.py` (a domain the
founder does not own) appears as a `mailto:` on every page footer (`SiteFooter.tsx:78`), the
contact page (`app/contacto/page.tsx:99`), the newsletter (`NewsletterSignup.tsx:20`), the
homepage publish fallback (`app/page.tsx:96`), and — most seriously — inside `organizationJsonLd`
(`app/contacto/page.tsx:48`, `app/nosotros/page.tsx:70`, published to Google) and as the
GDPR/Ley 6534 data-rights address (`app/privacidad/page.tsx:166`). `app/proyecto/[slug]/page.tsx:245`
renders the literal string "propia.com.py" as a label.
*Fix:* one `src/config/contact.ts` exporting `CONTACT_EMAIL`/`CONTACT_WHATSAPP` from env with a
real default; import in those files; the proyecto label becomes `brand`. This is also the
template abstraction (§5).

**F11 — Rollback of updated rows loses images + poisons content_hash.** `SNAPSHOT_COLUMNS`
(`src/lib/import/upsert.ts:300`) captures scalar columns only, but the `updated` branch runs
`syncImages()` which deletes and re-inserts `listing_images`. Rollback restores scalars and not
images — curated/uploaded photos are gone. And rollback doesn't revert
`listing_sources.content_hash`, which commit already advanced, so re-importing a *corrected*
file hashes identical → reported `unchanged` → the fix is never applied.
*Fix:* snapshot image rows into `previous_json`, and reset `content_hash` on rollback.

**F12 — Rollback of `deduped` rows is a no-op.** The delete predicate is
`first_seen_at >= job.createdAt` (`src/lib/import/jobs.ts:364`), but the job header is created
*after* commit, so every source row written by the commit has `first_seen_at` strictly before
`job.createdAt` — zero rows deleted, yet the job is stamped `revertedAt` and the UI claims
success.
*Fix:* record the commit start timestamp (create the job header before commit) and compare
against that.

**F13 — Resync pauses agent-claimed listings.** `FEED_SOURCES` (`src/lib/import/resync.ts:26`)
includes `import_agency_site` etc., which is exactly what a link-claim stamps
(`src/lib/import/claim-import.ts:160`). A claim writes `last_seen_at` once and is never
re-imported, so 30 days after an agent claims and publishes their own property, the resync sweep
pauses it and it disappears.
*Fix:* restrict `FEED_SOURCES` to bulk feeds, or exclude sources whose row has never been
re-seen (`last_seen_at = first_seen_at`).

**F14 — Nothing ever un-pauses.** `resync.ts:9` promises "one re-import that sees it again is
enough to put it back", but `listingFields()` never touches `status` and the `unchanged` branch
(`upsert.ts:349`) only bumps `last_seen_at`; and `findStaleListings()` filters
`status='published'`, so a paused listing is invisible to the sweep too. Only a manual rollback
or hand edit recovers it.
*Fix:* in commit, if a matched listing is `paused` and its source row is being re-seen, restore
it to `published`.

**F15 — Stale cuota on operation/price change.** `scripts/recompute-cuotas.ts:44` selects
`operation='venta'` only, and `updateListing` (`src/lib/listing-edit.ts:252`) deliberately
leaves `cuota_gs` to the cron. A listing flipped venta→alquiler (or edited to a lower price)
keeps its old cuota forever, rendered on the card, detail page and map.
*Fix:* null `cuota_gs` in `updateListing`/`draftFields` whenever operation or price changes; or
drop the `operation` filter in the cron and let `bestCuota` return null for non-venta.

**F16 — Valuation/median sample inflated.** `scripts/compute-medians.ts:88` stores
`sample_size = b.prices.length` (all listings in the bucket), but `median_price_m2_usd` is
computed only from listings with an area. `/tasacion` (`src/lib/valuation.ts:116`) then sums
that inflated sample, tests reliability against it, and picks its confidence band from it — so a
bucket of 40 listings with 2 areas returns a ±15% band on a price/m² derived from 2 data points.
*Fix:* store the m² sample count separately (or write `sample_size = pricesM2.length` for the m²
median) and gate/weight the m² path on that.

**F17 — Every public page is dynamic; no route cache.** The root layout calls
`currentVertical()` → `await headers()` (`src/lib/vertical-context.ts:16`), plus SiteHeader /
Footer / Notice, forcing the whole tree dynamic — including ~25 static marketing/legal pages.
`revalidate = 600` on the home page (`app/page.tsx:72`) is dead code as a result. On a
200-process shared cap, a crawler walking the sitemap is N full renders — the 503 pressure
class.
*Fix:* resolve brand/theme in `middleware.ts` (it already runs) and pass via header/cookie so
the render path doesn't call `headers()`; or split a `(static)` route group whose layout doesn't
resolve the vertical; and wrap the home payload in `unstable_cache`. This is the single
highest-leverage perf change.

**F18 — Contact form always reports success.** `src/components/ContactForm.tsx:66` has an empty
`catch` and a `finally` that sets `setSent(true)` unconditionally. If `/api/leads` 400s and
`contactWhatsapp` is null (F4), the visitor sees "¡Mensaje enviado!" with zero delivery.
`LeadForm.tsx` does check `res.ok` — two components, two behaviours.
*Fix:* check `res.ok`; only claim success when the POST succeeded or WhatsApp opened. Also open
WhatsApp via an `<a target="_blank">` rather than a post-await `window.open` (popup-blocked on
iOS).

**F19 — safe-fetch buffers the whole body.** `src/lib/safe-fetch.ts:158` checks
`content-length`, then `await res.arrayBuffer()` reads the entire body regardless. A server that
omits/lies about the header streams unbounded bytes into a shared-host process's heap.
*Fix:* read `res.body` via a reader loop, aborting past `MAX_BYTES`.

**F20 — No security headers / CSP.** `next.config.ts` has no `headers()` block — no CSP,
`X-Content-Type-Options`, `Referrer-Policy`, `frame-ancestors`. A `script-src 'self'` CSP would
have contained F2.
*Fix:* add a `headers()` entry; CSP needs a nonce or `'unsafe-inline'` allowance for the JSON-LD

**F21 — Password/email change needs no re-auth.** `src/lib/profile-queries.ts:154`

takeover, and the change then revokes all *other* sessions, locking the real owner out.

**F22 — Brand doubled in `<title>`.** `app/proyecto/[slug]/page.tsx:53` appends `| ${brand}`

**F23 — Homepage has no canonical.** `app/page.tsx:74` sets no `alternates`, so `?utm_*` /

## 5. Templatization

**Recommendation: single multi-vertical engine (one repo, one deploy, config-per-host) — for
markets that share the codebase, which is most of them.** This repo is already built for it:
`verticals.ts` + `middleware.ts` + `origin.ts` resolve host→vertical→brand, the sitemap and
canonical machinery are host-aware, and one DB/admin serves every domain. Forking per client
would mean hand-syncing every fix (and every one of the 60+ findings above) across N copies —
PLAN.md D6 already reached this conclusion for the two-domain case, and it scales to markets.

**The nuance for `flyttatillspanien.se`:** a Swedish-buyer / Spanish-property site is a
*different market and language*, not just a different host. The engine is genuinely reusable, but
the currency/financing/location/i18n/taxonomy assumptions below are hardcoded deep enough that
the honest split is: **one engine repo whose Paraguay specifics are extracted into config, from
which each market is a config-and-content layer, not a fork.** Cut the template only after the
TEMPLATE-CRITICAL items are fixed in the live site — otherwise every fix is done N times.

`src/lib/origin.ts`, `src/lib/jsonld.ts`, `src/lib/vertical-context.ts`, `src/lib/r2.ts`,

schema *structure*, and the scripts. These are market-neutral.

### Hardcoded assumptions that must become config
- **Currency.** `price_currency` enum is literally `["USD","PYG"]` (`schema.ts:79`) and the union
  `"USD" | "PYG"` is written by hand in **17+ files** with no `Currency` type alias. `es-PY`,
  `Gs `, `US$` hardcoded in `format.ts:6`. `USD_TO_PYG` default duplicated in two files. **A new
  currency is a 20-file find-and-replace with no compiler help on the DB enum.**
- **Financing.** `cuota_gs` — the column name encodes the currency, and it reaches cards, map,
  detail page, cron and edit (10 files). `che_roga_pora` special-cased in the detail page and nav.
  The amortization *engine* transplants cleanly; the column name and labels do not.
- **Locations.** `level` enum `["pais","departamento","ciudad","barrio"]` (`schema.ts:187`) fixes
  the hierarchy at four Spanish-named levels, and `parseCategorySegments` (`urls.ts:105`) hardcodes
  city[/barrio][/type]. A market with a different administrative shape rewrites the routing.
- **Taxonomy.** The property-type enum is duplicated across the DB enum + **5 parallel maps**
  (`property-types.ts`, `urls.ts`, `photos.ts`, `import/types.ts`, and a straight duplicate at
  `app/[operacion]/[...segments]/page.tsx:47`); operation across 6. TypeScript catches four, not
  the DB enum.
- **i18n.** `@/i18n/es` is imported by name in ~40 files while `vertical.locale` already exists and
  is ignored. "Add a language" currently = "add 40 imports".
- **Phone/WhatsApp.** `canonPhone` strips `595`+leading-0 (`normalize.ts:33`), corrupting any other
  country; 9 raw `wa.me` builders; `🇵🇾 +595` hardcoded in three form components. WhatsApp-first is
  itself a *market* assumption — Sweden is not a WhatsApp market, so the primary CTA is strategy,
  not a constant.
- **Domains/brand outside verticals.ts** — `realestateinparaguay.com` in publish-wizard copy
  (`es.ts:20`), the safe-fetch user-agent, `R2_PUBLIC_BASE_URL` default, `BRAND_KICKER="Paraguay"`,
  `brandTaglineFor` "…in Paraguay", the proyecto literal.
- **Legal/timezone** — Ley 6534 in the privacy page, PY footer, and **no `TZ` handling anywhere**
  (`new Date()` runs in server-local zone for publish-ago, OTP expiry, featuredUntil) — a latent
  cross-market bug.

## 6. Checked and found genuinely fine (don't re-audit)

- **Session security** — httpOnly/secure/sameSite/path cookie flags, 256-bit token stored only as
  sha256, server-side expiry enforced, fresh token per login (no fixation), logout + password-reset
  revocation all correct (`src/lib/auth/session.ts`, `password.ts`).
- **Route protection** — no admin/agencia layout to lean on; every one of the 12 admin + 6 agencia
  pages guards itself, and every mutating server action re-invokes its guard rather than trusting a
  layout. Scope enforcement (`listingScopeWhere`/`panelScope`/`EditScope`) is in the WHERE clause,
  cross-tenant isolation holds, admin self-lockout guards present.
- **SQL injection** — none. No `sql.raw`/`sql.identifier`/interpolation; no user-controlled ORDER
  BY; Drizzle parameterises the LIKE terms (F52 is a wildcard-escaping nit, not injection).
- **Secrets** — no `process.env` in any client file; DATABASE_URL / R2 / ANTHROPIC keys never reach
  the bundle; no env file committed.
- **Import correctness core** — plan and commit share one planner (commit re-plans from raw bytes),
  external-id scoping matches `uq_source`, phone normalisation collapses all PY formats correctly,
  French amortization math is correct (nominal monthly rate, down-payment and cap applied, integer
  Gs), no currency column can overflow, null/zero price into cuota yields NULL not NaN, ownership
  never reassigned on re-import, resync can't touch hand-typed listings, median bucketing never
  mixes operation/currency.
- **Perf already done** — pool bounds + timeouts, health endpoints, `React.cache` on category/detail
  loaders, the Promise.all parallelisations, `COUNT(*)` conversions, `attachCovers` single-query
  (no card N+1), thumbnails use the 480px derivative, LCP handling (fetchPriority/eager on hero and
  cover, lazy elsewhere), CLS reserved via fixed aspect boxes, maplibre lazy-loaded, login
  rate-limiter memory swept.
- **Multi-host core** — `origin.ts` host normalisation (www/port/case/comma-list/unknown-host
  fallback), `hostOwnsListingDetail`/`listingCanonicalOrigin` share one predicate so sitemap and
  canonical can't drift, detail-page canonical + og:url correct on both hosts, category canonical
  strips all query params (no ?vista=mapa dupe), indexability called by both templates and sitemap,
  `verticals.ts` keys unique. **The BRAND_NAME sweep is clean** — exactly one import of
